# 2026-11-15 性能与并发优化（第一轮）

> 代码质量分析后的第一批落地优化。原则：**只做低风险高收益修复，不改变任何对外行为语义**；
> 全量回归与基线对比通过后打包。涉及 FX 卡顿、并发容器、锁内 IO、内存治理与机械性代码质量。

## A 批：FX 线程卡顿修复

| 修复 | 位置 | 说明 |
|---|---|---|
| MCP「重连」移后台线程 | `SettingsDialog.mcpPane` | 原同步等待 ≤10s 直接冻结整个界面；现后台执行 + runLater 刷新，按钮期间禁用防重复点击 |
| 附件解析移后台线程 | `InputView.addAttachments` / `addClipboardImage` | 图片解码/文档提取/PNG 编码改到 `attachmentPool`（daemon 单线程）；上限校验与 addChip 回 FX 线程按最新块计数判定；GD 弹窗经 `chooseGdExportOnFx` 回 FX 线程执行并等待 |
| 定时任务 tick 移出 FX | `SessionManager` 构造器 jobClock 调度 | `tickJobs` 直接在 jobClock 线程执行（账本读取/目录扫描是磁盘 IO）；派发走 `send`（后台线程安全），界面刷新由监听器自行 runLater |

## 明确不做（本轮）与原因

- **StreamRecoveryPolicy / StopAdjudicator / CompactionService 拆分**：AgentLoop 深度手术，回归面大，留给独立版本（ReplyHeuristics 已解开反向依赖，是后续拆分的第一步）
- **DeepSeekClient 拆 ProviderAdapter**：同上，SFM/qwen 适配逻辑涉及协议行为
- **17 份参数取值 helper 统一**：跨 17 文件的行为统一（`getAsInt` vs `parseInt(getAsString)` 对 `"30.0"` 等输入行为不同），需逐工具测试确认，单独一轮做
- **slf4j 日志迁移 / CSS 死样式清理 / 状态字符串枚举化**：宽而浅，收益与风险比不高

## 第三轮：修复"报错 + 该停停不下来"（完成门禁死锁）

**用户实证**：会话 20261115-202508-678-0001 中模型两次明确答复"已核对无副作用"，任务仍被
完成门禁无限 block 强制续跑 25 轮，最终一次 HTTP 400 使任务 paused。

**根因链（三处）**：
1. `ToolExecutionGuard` 两处 `reliability.finish()` 不在 finally——工具抛异常（如本机无 Python 的
   exit 49）时步骤永久停在 `started`，进入 `pendingMutations` 永不解除；
2. `ReliabilityService.acknowledge()`（uncertain/started 步骤的唯一解除出口）**没有任何工具入口**——
   模型只能口头说明"已核对"，门禁不认，形成"不让结束、也不让重跑"的死锁；
3. 无限强制续跑后模型接口一次 400（请求体配对已核验完好，疑服务端/网关侧），任务 unclassified 暂停。

**修复**：
| 位置 | 改动 |
|---|---|
| `ToolExecutionGuard.executeCore` 两处 | `finish` 移入异常兜底：工具异常时按"结果不确定"收账（mutation → uncertain），不再永久 started |
| `AgentControlTool` | 新增 `verify_step(stepId,note)` 动作暴露 `reliability.acknowledge`；description 写明用法与"禁止编造"约束 |
| `AgentLoop` 门禁文案 | block 与 waiting_user 提示均附步骤 ID 清单与解除指引（"只读核对后 AgentControl verify_step 解除"） |

**数据解救**：当前会话账本中 3 个卡住步骤（1 started Python + 2 uncertain Bash）已人工标记
verified（含核对说明），重开会话即可正常收尾。

**验证**：新增 `TaskWorkflowToolTest.verifyStepReleasesUncertainJournalEntries`（started/uncertain
两场景：缺 note 拒绝、解除后 unresolved 清空、重复解除拒绝）；StopGate/EvidenceBased/
ProgressContinuation/TaskWorkflow 共 46 项全过；AgentLoop 相关 194 项回归，失败集合与 A/B
基线完全一致（零新增）。

**遗留**：400 偶发根因未定位（请求配对与参数合法已排除），表现为任务 paused 可续跑；后续可在
DeepSeekClient 记录 400 响应体全文后再排查。

## 第四轮：任务结束判定对齐主流 Agent（彻底修复"停不下来"）

**用户实证**：查询类任务，模型查完（12 轮工具）给出实质结论答复 5 次，每次都被
"目标要求文件或程序产出，但当前回合没有可核验的成功工具"拦截强制重跑，用户手动 Esc。

**主流调研（Codex / Claude Code / ZCode / Cursor 的共同设计）**：
1. 模型的最终答复（无工具调用的正文）即回合结束，运行时不做语义二次盘问；
2. 防未完成靠**系统提示词约束 + 模型能力**，不靠运行时门禁循环；
3. 运行时只做**机械性续接**：截断（length）、空回复、流错误；
4. Claude Code 的 Stop-hook 是用户显式 opt-in 的扩展点，且默认无。

**Minion 保留差异**（本地弱模型遗产）：零工具纯计划回复仍会被防懒网拦截，但预算收紧。

| 改动 | 内容 |
|---|---|
| 直接完成范围扩展（AgentLoop 决策级联首分支） | 普通模式下"实质答复直接完成"从纯问答合同扩展到**本轮已有成功工具回执**的产出型合同（source=normal_answer）。真实工作后的交付答复不再被二次盘问 |
| localProof 防懒分支收窄 | 拦截条件从"mutation 且无文件证据"收紧为"mutation 且整轮**零工具回执**且回复是**纯计划签名**（looksLikeInterimAnswer）"——不再拦截有真实工作的答复 |
| 无进展预算 12→4 | StopGate.NO_PROGRESS_LIMIT 收紧；防懒催促最多 4 次后显式暂停（原来 12 次既浪费又造成"停不下来"体感） |
| 只看本轮回执 | 历史回合旧证据不能替新任务完成判定，防偷懒计划借旧证据混过门禁 |

**安全性保留**：副作用未知（uncertain 步骤，第三轮已加 verify_step 出口）、未核对子任务、
明确用户依赖（waiting_user）、GOAL/REVIEW 模式独立核验——均不受本轮放宽影响。

**验证**：新增用户场景回归测试（两轮查询+实质结论=3 请求完成，不再重跑）；更新 4 处锚定旧行为
的断言（预算次数 14→6/16→8、完成来源标签）；完成判定相关 8 类 130 项测试通过；全量 2272 项
失败集合与基线一致（唯一新增为子代理预算断言，已随语义更新）。

## 第五轮：完成标记不再显示

用户反馈：最终答复末尾的 `[[MINION_TASK_COMPLETE]]` 出现在聊天区。该标记是完成门禁的内部记号
（系统提示词第 10 条要求模型追加），此前渲染层未剥离。

**修复**：`ChatView.stripTaskMarker` 在展示层剥离——仅影响显示，事件流/会话落盘/门禁判定保留原文；
流式跨分片的未完成前缀（如 `[[MINION_`）暂不显示、下一增量补齐；普通正文 `[` 结尾不受影响
（`[[` 起步才识别）；每 delta 调用走 regionMatches 零分配。主回复与子 Agent 输出两个渲染点均接入，
历史会话重放同样生效。`AgentLoop.TASK_COMPLETE_MARKER` 改 public 供 GUI 复用同一常量。

## 第六轮：外部审查确认项修复（主流实现对照）

  tools/handlers(工具处理)；回合由最终 assistant 消息结束（与第四轮对齐一致）。→ AgentLoop 拆分按此路线。
- **版本治理**：小步提交 + CI 全绿门禁。
