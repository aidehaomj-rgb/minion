# Minion：DeepSeek V4 Pro / Qwen3.8 Flash 的 1M 模型调优

> 后续变更：自动压缩默认稳定工作区已调至 150K；DeepSeek 与 Qwen3.8-Flash 旧 80K/120K 配置会一次性迁移。见 [自动压缩 150K 开发说明](自动压缩150K-开发说明.md)。下文的 80K/120K 是当时的配置与试验建议，并非当前默认值。

状态：仅本地源码；尚未制 Win7 更新包，也未连接内网服务实测。

## 原则

1M 是接口宣称可容纳的上限，不是每次请求应达到的目标。用户已观察到约 200K 后变慢、误停和错乱；要优化的是任务完成率、工具调用可靠性和长对话可检索性，不是单轮送入 token 最大值。原始会话事件和用户纠正照常持久保存，压缩只改工作上下文；需要旧证据时按需检索，而不是从压缩摘要猜测。

公开接口文档显示 [DeepSeek V4 Pro](https://api-docs.deepseek.com/quick_start/pricing/) 和 [Qwen3.8 Flash](https://help.aliyun.com/en/model-studio/qwen3-8-flash) 的云端版本提供约 1M 上下文与工具调用，但**内网部署的网关、模型快照、视觉/思考协议及实际容量必须单独验证**。尤其官方 DeepSeek V4 Pro 列为不支持视觉，Qwen3.8 Flash 列为支持图像/视频；不能因此断言本机网关一定一致，也不应自动把有图任务静默转到另一个模型。

## 本轮代码行为

- 模型设置新增“稳定工作区 (token)”：`0` = 保守默认 120000；可以给每个模型设不同值，例如先从 Pro 120000、Flash 80000 或 120000 开始，用实测再调。它不修改 `maxContextTokens`，自动整理阈值取 **稳定工作区、百分比阈值、窗口减输出预留** 三者的最小值。`stableContextTokens` 持久化在 `model.json`；旧配置缺少该字段时仍按 120K 默认运行。
- 模型切换及子 Agent 的运行时配置均传递该模型工作区；图形界面的预览和上下文圆环显示实际触发点，超过 200K 会提示需实测。
- 服务端超限或零增量超时仍按当前会话观察值下调窗口并优先压缩。人工配置较大的工作区不能越过更小的会话安全窗口。
- `model-health` 诊断日志记录每次主 Agent 请求的估算/实际输入、输出、首个输出延迟、总耗时、完成原因、工具调用数和异常类别，不记录正文。日志在 jar 同目录的 `.minion/logs/minion.log`；实际 token 缺失时为 0，不能当作真实消耗。**仅主 Agent 有这项新统计，子 Agent 仍有其既有的任务状态/上下文统计。**

## 内网校准顺序（不要预设 Pro 一定比 Flash 更适合所有任务）

1. 保持两个模型各自正确的 URL、模型名、API Key、provider、思考参数。用相同的只读任务分别验证工具调用、流式首字、finish reason、usage 和图片输入支持；检查本地模型协议是否接受所有请求参数。
2. 用真实的长任务回放，从 80K、120K、160K 再到 200K 梯度调整稳定工作区；只有上一档的首字延迟、超时率、工具调用合法率、StopGate 判断和最终验收都稳定，才提高下一档。不同模型可选不同值；不建议直接设 1M。
3. 分任务对照：复杂代码修改与结束核验可先试 Pro；高频查找、资料分块、视觉材料可先试 Flash。但这是**待实测的路由建议**，不是硬编码的能力排名。现有子 Agent 可显式选模型；自动路由要等内网数据证明净收益后再加。
4. 评估长对话时至少回放：200K 后改用户要求、连续压缩、分块子 Agent、模型切换、文件内容已变化、故意不给证据的“已完成”说法。判定顺序是最新指令优先、证据能找回、不重复已完成操作、不跨项目泄漏、最后才看 token/速度。

## 后续高价值优化

- 真正的**模型能力探测与协议配置**：明确网关支持的 tool choice、思考开关、usage、视觉、并发和输出限制，避免按模型名猜协议。
- 对每种模型建立可回放基准，并统计 P50/P95 首字时间、长任务完成率、无效工具调用率、用户纠正保持率和检索额外 token；以数据决定工作区及是否需要任务级模型路由。
- 对大量文件、Excel、SQL 的分析仍优先让工具分块计算并注入结果/证据位置；1M 上下文不替代真实执行、数据校验或可靠记忆。
