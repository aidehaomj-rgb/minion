# V48 开发版：成果预览、文件交付与引导回执

日期：2026-11-06。本轮按用户要求继续开发右侧报告栏，不改动已交付的V47小更新ZIP，不自动安装，不推送GitHub；本轮是否出更新包须另行提出。

## 对照公开产品体验

- [OpenAI官方 Work with files](https://learn.chatgpt.com/docs/artifacts-viewer)：桌面应用可在聊天旁预览生成的文档等文件；预览能力因桌面、CLI、IDE表面不同。本轮借鉴“生成文件与聊天并排、产物路径清楚可打开”的交付方式，不声称复制了全部编辑/批注功能。
- [Claude官方 Artifacts说明](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them)：独立成果侧栏与查看/导出。本轮借鉴“成果独立于回复、可切换、可外部使用”，不接入云端服务，也不照搬需现代浏览器/云端运行时的功能。
- “右键打开文件位置、复制路径、另存为”是针对当前Windows本地工作流的设计，不将没有来源证明的具体菜单行为归于其他产品。

## 原有差距

1. 原右侧栏只同步读取UTF8 Markdown；Word二进制会被误当文本，读取还阻塞JavaFX线程。
2. 只有一个lastArtifactPath，自动执行记录容易盖过真正交付的报告。
3. Markdown链接在转纯文本时丢失href；用户看到文件名却无法点击到原文件。
4. 缺少文件位置/复制路径/另存为等统一动作，以及会话重启后的成果目录。

## 本轮实现范围

### 右侧成果工作区

- 区分真实交付物、引用文件、执行记录；会话内最多保留100个文件引用，重复修改同一路径更新记录。当前任务的交付物优先于自动执行记录，不把旧任务文件当成当前任务成果。
- 文件选择器、目录跳转、预览/文本切换、复制全文、刷新、外部打开、定位文件、另存为。
- 文件切换/会话切换通过请求代际丢弃旧读取结果；加载在后台，有界队列只保留最新请求，不阻塞流式聊天。
- 可关闭“跟随新成果”；手动选择旧文件后不被新文件抢走。关闭右侧栏后本轮不会被每次写入强行重开。
- 保留用户拖动的报告栏宽度，不在每次文件刷新时重设分隔条。

### Markdown与Word

- Markdown保留标题、段落、列表、表格、代码及链接。文本模式保留源文，可分页复制。
- DOCX使用JDK8内置ZIP/XML读取正文、标题、基础加粗、列表、表格与受限内嵌附图；不依赖Python、Office、网络或新的Java依赖。
- **这是内容预览，不是Word分页排版完全保真，也不是Word编辑器**。分栏、复杂页眉页脚、分页、公式、批注等仍请用Word/WPS查看。
- 旧`.doc`、加密或损坏文件明确提示，不把二进制按UTF8输出乱码；旧`.doc`可一键用系统关联的Word/WPS打开，或另存为`.docx`后预览。
- 文本/ZIP条目/XML/图片像素和数量均有界；大文件清楚标注预览截取，原文件不改写。远程图片、外部Office关系、HTML脚本和宏不自动加载/执行。

### 文件链接与交付

- 标准Markdown链接的目标不再在纯文本处理中丢失。聊天当前分页提供有界可点击链接，生成文件另有文件卡片；链接中中文、空格、`#`/`+`等通过file URI编码保留。
- 单击文件链接或“打开文件”交给系统关联应用；右键支持右侧预览、打开文件、打开文件位置、复制完整路径、复制文件链接、复制文件和另存为。
- 原文件引用可恢复到历史会话；文件已移动/删除时提示，不伪报文件仍存在。
- 只登记实际成功且授权范围内的文件。模型文字链接单独标为引用，不伪装成工具已生成；失败工具或旧任务迟到结果不登记为当前成果。
- 来源代码/可执行文件不会由聊天链接直接运行；可预览源码或定位后自行用编辑器/系统处理。不把打开文档变成命令执行入口。
- 不向模型追加伪造用户指令，不因文件存在就改变任务完成判定，不改变150K压缩目标。

## 回归重点与边界

验证实际DOCX正文/表格、坏ZIP/DOCTYPE/外链、UTF8/UTF16/GB18030与截取边界；消息分页和跨页链接、长流不额外逐token解析链接；真实AgentLoop成功写入→成果登记→执行记录链接→保存/恢复；切换文件时旧后台读取不得覆盖新文件；文件动作只在明确用户手势触发，测试使用假后端避免打开真实用户文件。

最终完整回归 **2070项，0失败、0错误、3项跳过**；初次定向集成245项与恢复边界专项59项均无失败，不叠加次数当成覆盖数。Java8构建、最终JAR字节码/源码快照及原生JavaFX截图已验证，见 [验收结果](V48-开发验收结果.md) 与 [详细JSON](V48-开发验收结果.json)。开发机与替身测试不等于真实Win7、Office/WPS关联程序或资源管理器实点击已验收。

## 追加需求：立即引导“未读／已读”

对照 [Kimi Code官方《输入与上下文》](https://www.kimi.com/code/docs/kimi-code-desktop/input-and-context.html) 中的插队消息未读、已读和插入进度，新增引导送达回执。这里仅借鉴可观察性，不复制其私有实现，也不依赖Kimi服务。

- 尚未点击“立即引导”的草稿/普通下一任务队列，与已经发出的引导分开。
- 已提交的引导有稳定ID，显示排队未读、已插入等待发送、发送中、已读或未确认待重试，保留时间和请求关联。
- **“已读”只表示该条引导确实包含在主模型业务请求中，且该请求已收到有效响应；不保证模型理解正确、照做或任务已完成。** 当前请求已经发出后，不能把新文字倒灌进原请求；需要等安全检查点和下一次业务请求。
- 请求失败、只有空心跳、子Agent/压缩/核验响应，不应把当前新引导标成已读。流式过程中才到的新引导不能被旧请求回执提前确认。
- 聊天原引导行更新状态，不重复追加正文；输入栏可查看本会话的引导送达记录。重启和会话切换不能串状态。
- 保留最近100条送达记录；恢复时先按ID合并已有状态，再按原时间统一裁切，避免旧记录连锁挤掉近期已读。原始消息/事件不因界面列表裁切而删除，也不会借回执把旧任务重新塞进当前上下文。
- 旧版本没有回执ID的历史消息不能追溯证明已读，不会凭出现过相同文字补造已读状态。
- 不为回执额外调用模型，不将回执写入永久记忆，不据此判定任务完成，150K压缩目标保持不变。
